# Go-бэкенд JOSPAT

Бэкенд включает регистрацию по email, подтверждение адреса, вход с ограничением попыток, восстановление пароля, API календаря и планировщика и импорт из старой копии JOSPAT. Интерфейс в корне проекта по-прежнему работает с браузерным хранилищем. Сервер можно проверять отдельно через HTTP.

## Локальный запуск

Понадобятся Go 1.26 или новее и PostgreSQL с отдельной базой для JOSPAT. В PowerShell из папки `backend` выполните команды ниже, подставив адрес своей базы. Переменные задаются в текущем окне PowerShell.

```powershell
$env:DATABASE_URL = 'postgres://jospat:your-password@127.0.0.1:5432/jospat?sslmode=disable'
$env:JOSPAT_INSECURE_DEV = '1'
go run . migrate
go run .
```

Сервер по умолчанию слушает `127.0.0.1:8080`. Режим `JOSPAT_INSECURE_DEV` предназначен для локального HTTP. Для развёртывания понадобится HTTPS. Внешний адрес прослушивания можно задать через `JOSPAT_ADDR`.

Если база уже создана, повторно выполните `go run . migrate` перед запуском нового сервера. Миграция добавляет таблицы подтверждения email, восстановления и ограничения попыток. Ранее созданные аккаунты сохраняют записи и впервые подтверждают адрес через `/api/auth/resend-verification`. До подтверждения вход и доступ через старые сессии закрыты.

## API первой версии

| Запрос | Действие |
|---|---|
| `GET /healthz` | Проверить доступность базы |
| `POST /api/auth/register` | Создать аккаунт через `email` и `password` и поставить письмо с кодом в очередь |
| `POST /api/auth/verify-email` | Подтвердить email через `token` и установить `password` для входа |
| `POST /api/auth/resend-verification` | Запросить новый код подтверждения по `email` |
| `POST /api/auth/login` | Войти и получить сессионную cookie |
| `POST /api/auth/forgot-password` | Запросить код восстановления по `email` |
| `POST /api/auth/reset-password` | Сменить пароль через `token` и новый `password` |
| `GET /api/auth/me` | Получить текущий аккаунт |
| `POST /api/auth/logout` | Закрыть текущую сессию |
| `GET /api/events?from=2026-11-01&to=2026-11-30` | Получить события своего аккаунта. Обе границы включены. Без параметров возвращаются все события. |
| `POST /api/events` | Создать событие |
| `PUT /api/events/{id}` | Обновить событие с заголовком `If-Match` |
| `DELETE /api/events/{id}` | Удалить событие с заголовком `If-Match` |

Запросы с JSON используют `Content-Type: application/json`. Пароль содержит от 12 символов, до 512 байт. После регистрации или повторного запроса возьмите код из письма и передайте его в `verify-email` вместе с выбранным паролем. Можно повторить пароль из регистрации. Подтверждение устанавливает пароль, который выбрал владелец почты. После ответа `204` выполните вход. До подтверждения корректный пароль возвращает `403 email_not_verified`. У сессии срок жизни семь дней. Маршруты событий и планировщика используют ту же cookie.

Код подтверждения действует 24 часа, код восстановления для подтверждённого аккаунта — один час. Оба одноразовые. Повторная отправка оставляет предыдущий код действительным до истечения срока или первого успешного использования. Запросы кода возвращают одинаковый `202` независимо от существования аккаунта. После сброса сервер закрывает все сессии аккаунта, аннулирует остальные коды восстановления и ставит в очередь уведомление о смене пароля.

На вход выделяется 5 попыток на email и 25 на IP за 15 минут. При превышении сервер возвращает `429` и число секунд до следующей попытки в `Retry-After`. Отдельные лимиты действуют для регистрации, запроса писем и ввода кодов. Счётчики находятся в PostgreSQL. Сервер учитывает `X-Forwarded-For` только от прокси в `JOSPAT_TRUSTED_PROXIES` (список CIDR через запятую). При развёртывании за прокси укажите его фактические диапазоны. Прокси должен добавлять фактический адрес клиента в конец цепочки.

### Отправка почты

При локальном запуске с `JOSPAT_INSECURE_DEV=1` и без настроек SMTP коды появляются в окне сервера. Скопируйте код из строки `local auth code`. Его можно проверить через API, передав файл с JSON, как при тесте входа.

```json
{"token":"КОД_ИЗ_КОНСОЛИ_ИЛИ_ПИСЬМА","password":"выбранный пароль для входа"}
```

В развернутой версии задайте переменные почтового провайдера. Настройки SMTP обязательны при запуске с защищёнными cookie.

| Переменная | Значение |
|---|---|
| `JOSPAT_SMTP_ADDR` | Хост и порт SMTP-сервера |
| `JOSPAT_SMTP_FROM` | Подтверждённый адрес отправителя у почтового провайдера |
| `JOSPAT_SMTP_USER` | Логин SMTP |
| `JOSPAT_SMTP_PASSWORD` | Пароль или ключ SMTP |
| `JOSPAT_SMTP_TLS` | `starttls` по умолчанию или `implicit` для порта с TLS с самого начала |

Письма отправляются в фоне. `201` при регистрации и `202` при запросе кода подтверждают принятие запроса сервером. Если доставка не удалась или сервер перезапустился, запросите код снова. В письме приходит код для соответствующего POST-маршрута. Ввод кода на сайте потребует подключения фронтенда.

Тело запроса при создании события соответствует полям браузерной версии.

```json
{"id":"event-1","name":"Встреча","date":"2026-11-28","time":"15:30"}
```

Поле `id` необязательно при создании. Можно передать идентификатор из существующей записи. Дата и время описывают локальные дату и время из текущего интерфейса. В ответе появится `version`. Для правки или удаления версии 1 передайте `If-Match: "1"`. Если версия изменилась, сервер возвращает `412`, и клиенту нужно перечитать запись.

## API планировщика

Все маршруты планировщика требуют активной сессии. Для операций с существующей задачей передавайте её текущую версию в `If-Match` по тем же правилам, что и для событий.

| Запрос | Действие и данные |
|---|---|
| `GET /api/tasks` | Возвращает `tasks` в порядке добавления, пустой `overdue` и текущий `taskOrder`. |
| `GET /api/tasks?date=2026-11-28&today=2026-11-29` | Возвращает список за выбранный день, уже отсортированный с подзадачами после родителя. `today` нужен для списка просроченных. |
| `POST /api/tasks` | Создаёт задачу из `name` и `date`. Дополнительные поля — `id`, `parentId`, `project`, `time`, `priority` от 0 до 2. При наличии `parentId` сервер берёт дату родителя. |
| `PUT /api/tasks/{id}` | Редактирует `name`, `date`, `project`, `time` и `priority`. Можно передать только обязательные `name` и `date`, остальные значения будут очищены. |
| `PATCH /api/tasks/{id}` | Меняет только `name`. Пустое название удаляет задачу, как в быстром редактировании планировщика. |
| `DELETE /api/tasks/{id}` | Удаляет задачу. Прямые подзадачи становятся самостоятельными и теряют ручные позиции. |
| `POST /api/tasks/{id}/move` | Переносит задачу на `date` или под `parentId`. При переносе под родителя используется его дата. Для ручной расстановки можно передать `"placement":{"id":"task-2","after":true}`. |
| `PUT /api/tasks/{id}/done` | Устанавливает `done` и вычисляет `doneLate` по переданной локальной дате `today`. |
| `PUT /api/tasks/{id}/featured` | Устанавливает `featured`. На день может быть одна главная задача. |
| `POST /api/tasks/copy-today` | По локальной дате `today` копирует задачи на следующий день, сохраняя иерархию, сбрасывая выполнение и пропуская уже скопированные записи. Возвращает `date` и `copiedIds`. |
| `PUT /api/task-order` | Сохраняет `taskOrder` для аккаунта. Значения — `priority`, `added`, `name`, `manual`. |

Задачи возвращаются в плоском формате планировщика с `parentId` для связи и серверной `version`. У задачи может быть один уровень подзадач. При изменении даты родителя даты подзадач обновляются в той же транзакции. Перенос родителя в подзадачи делает его прежние подзадачи соседями на том же уровне. Перестановка через `placement` включает ручной порядок. После операции, которая затрагивает несколько задач, перечитайте план, чтобы получить их новые версии.

Даты передаются в формате `YYYY-MM-DD`. Для `today` используйте календарную дату пользователя, которую показывает интерфейс. Это важно для корректной работы около полуночи. `422` означает, что родитель или задача для ручной перестановки недоступны для этой операции. `412` означает устаревшую версию.

## Интеграция

Для интеграции браузер будет обращаться к `/api` на том же адресе, с которого загружен сайт. Подключение экранов, формы подтверждения и кнопки импорта потребует изменения фронтенда. Календарь также показывает шаги целей по датам, они потребуют отдельного API.

## Импорт старой копии JOSPAT

`POST /api/import/jospat` принимает JSON из браузерного экспорта `jospat-backup` версии 1. Отправьте файл с `Content-Type: application/json` и cookie активной сессии. Обязательны массивы `data.events` и `data.tasks`, даже если один из них пуст. Импорт обрабатывает эти массивы и необязательный `data.taskOrder`. Другие разделы копии и вложения не сохраняются на сервере.

Пример для локального сервера и существующего аккаунта в PowerShell.

```powershell
$api = 'http://127.0.0.1:8080'
$credential = Get-Credential -Message 'Введите email и пароль JOSPAT'
$login = @{
    email = $credential.UserName
    password = $credential.GetNetworkCredential().Password
} | ConvertTo-Json -Compress
Invoke-RestMethod -Method Post -Uri "$api/api/auth/login" -ContentType 'application/json' -Body $login -SessionVariable jospatSession
Invoke-RestMethod -Method Post -Uri "$api/api/import/jospat" -ContentType 'application/json' -InFile '.\jospat-2026-11-29.json' -WebSession $jospatSession
```

Успешный ответ содержит отдельные счётчики для событий, корневых задач и подзадач.

```json
{"events":{"created":1,"skipped":0},"tasks":{"created":1,"skipped":0},"subtasks":{"created":1,"skipped":0},"featuredConflicts":0,"taskOrderImported":true}
```

- Идентификаторы из копии сохраняются. Повторная загрузка пропускает обработанные идентификаторы, даже если запись позже удалили. Записи с теми же идентификаторами, которые уже есть у текущего пользователя, тоже пропускаются. Изменения в серверных записях сохраняются.
- Порядок записей в исходном массиве сохраняется. Подзадача может стоять перед родителем. Связь проверяется по итоговому плану аккаунта, включая уже существующие задачи. Родитель должен быть самостоятельной задачей на ту же дату.
- При конфликте главных задач на один день приоритет у существующей главной задачи, затем у первой подходящей записи в копии. Остальные записи импортируются как обычные и учитываются в `featuredConflicts`. Режим сортировки переносится при заполнении пустого плана, если у аккаунта ещё нет сохранённого режима.
- Все записи переносятся одной транзакцией. При ошибке данных сервер возвращает `422`, включая поле `error` и, когда применимо, раздел, позицию с единицы и идентификаторы. Такой запрос не сохраняет ни событий, ни задач.
- Лимит одного запроса — 32 МиБ и 10 000 событий и задач суммарно. Если файл больше 32 МиБ из-за вложений или других разделов, можно локально подготовить отдельный JSON с полями `format`, `version`, `data.events`, `data.tasks` и `data.taskOrder`. Сохраните исходную копию для остальных данных.

## Проверка

Запустите `go test ./...`. Для интеграционного теста задайте `JOSPAT_TEST_DATABASE_URL` с адресом отдельной тестовой базы. Тест создаёт временную схему, проверяет API и удаляет эту схему после выполнения.
